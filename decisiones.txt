Decisiones aprobadas - Bocatta POS
Fecha: 2026-05-21

Este archivo contiene solo decisiones ya aprobadas durante la conversacion.
Las ideas abiertas, observaciones y propuestas exploratorias viven en notas.txt.


1. Separar la app en tres experiencias

Se aprueba separar la app por intencion humana, no solo por permisos:

- Empleado.
- Admin en modo venta.
- Admin en modo gestion.

El flujo de empleado y el de admin en modo venta se llamaran, para esta
conversacion, flujo general.


2. Flujo general

El flujo general incluye la operacion diaria de mostrador:

- Entrar.
- Validar o unirse a turno.
- Vender.
- Cobrar.
- Generar ticket.
- Seguir vendiendo.
- Operar con internet inestable o sin internet.
- Hacer operaciones simples de caja.
- Cerrar turno/caja cuando corresponda.

El flujo general no debe mezclar gestion profunda del negocio.


3. Admin en modo gestion

El modo gestion es para configurar, revisar y auditar el negocio fuera del
ritmo de venta.

Aqui pertenecen:

- Productos.
- Precios.
- Catalogos.
- Recetas.
- Combos.
- Promos.
- Inventario completo.
- Produccion.
- Compras.
- Sucursales.
- Empleados.
- Sueldos.
- Zonas.
- Reportes.
- Apariencia.
- Mantenimiento.
- Diagnostico.


4. Puerta de intencion para admin

Cuando un admin entra y hay turno activo, la app debe distinguir claramente:

- Vender en mostrador.
- Gestionar negocio.

"Administrar tienda" es demasiado generico para esta decision.


5. Login y registro

Se aprueba mantener email como base de identidad porque Firebase ya esta
implementado y sirve para respaldo y recuperacion.

Para registro:

- Pedir email.
- Pedir nombre de usuario/operador.
- Pedir contrasena o PIN inicial.
- Pedir codigo de acceso.

El codigo de acceso define el rol:

- Codigo maestro/admin -> ADMIN.
- Codigo empleado -> VENDEDOR.

Esto mantiene la autorizacion del admin o dueno al crear usuarios, porque solo
ellos conocen los codigos.


6. Inicio de sesion diario

Se aprueba que, a futuro, el inicio de sesion permita:

- Email + contrasena/PIN.
- Nombre de usuario + contrasena/PIN.

La pantalla actual ya sugiere "ID de usuario / email" y "clave / PIN", pero el
codigo debe alinearse con esa promesa.


7. Gestion de empleados y seguridad

Se aprueba como necesidad futura:

- El admin debe poder resetear acceso de empleados si olvidan contrasena/PIN.
- El reset debe poder dejar una clave/PIN temporal 0000.
- Debe forzar cambio de clave/PIN en el siguiente inicio de sesion.
- Debe guardar auditoria.
- El admin debe poder modificar codigo maestro y codigo empleado desde gestion.

La UX no debe dejar al admin atado de manos: si una persona no puede entrar,
debe existir una salida clara y autorizada.


8. Pantalla de login aprobada

Se aprueba mantener una pantalla de login muy cercana a la actual, con ajustes
de texto y seguridad:

- Titulo principal de acceso.
- Campos para email o usuario.
- Campo para contrasena o PIN.
- Boton principal para entrar.
- Opcion para crear acceso autorizado.
- Sin opcion publica de "olvide mi contrasena".

La recuperacion/reset de acceso debe manejarse desde Admin dentro de la app,
para cerrar brechas de seguridad.


9. Apertura de turno por permiso

Se aprueba que iniciar turno/jornada no sea exclusivo de admin.

La apertura de operacion diaria debe depender de permisos configurables por
empleado o rol. Un empleado autorizado puede abrir turno aunque no haya un
admin presente.

Motivo:

- El admin puede no estar fisicamente presente.
- El telefono del admin puede no estar disponible.
- La operacion del negocio no debe quedar detenida si el admin ya delego ese
  permiso previamente.

Reglas aprobadas:

- Rol y permisos son conceptos distintos.
- Un empleado sin permiso no puede abrir turno.
- Un empleado con permiso puede abrir turno y empezar a vender.
- Si no hay turno y el empleado no tiene permiso, la app debe mostrar una salida
  clara: pedir a un encargado/admin que abra turno.
- Los permisos se gestionaran desde Admin > Empleados / Roles.


10. Produccion con flujo unico y dinamico

Se aprueba que no existan varias formas separadas de registrar produccion.

La app debe tener una sola accion mental:

- Registrar produccion.

Dentro de ese flujo, la configuracion del producto/preparado define como se
captura y que descuenta.

Reglas aprobadas:

- Un preparado se registra descontando materia prima y aumentando stock del
  preparado.
- Despues, en venta, se descuenta el preparado en piezas/porciones/unidad
  operativa, no otra vez la materia prima de su receta.
- La masa de crepa no sera una funcion especial hardcodeada. Debe ser un
  preparado configurable con receta, rendimiento y unidad operativa.
- Ejemplo: 1 tanda de masa = 60 porciones.
- Productos terminados como postres tambien entran por el mismo flujo de
  Registrar produccion, pero con captura por piezas u otra unidad configurada.
- La UI debe ser una sola, dinamica segun el tipo configurado.

Objetivo:

Evitar una UX fragmentada con varios caminos para "producir" y mantener un
modelo adaptable para otros giros.


11. Reclasificacion general

Se aprueba que la app necesita una reclasificacion general de productos,
insumos, preparados, consumibles y productos terminados.

Objetivo:

- Evitar programacion redundante en cada pantalla.
- Evitar reglas duplicadas en ventas, inventario, produccion, apertura, cierre,
  reportes y sync.
- Configurar por relevancia operativa y categorias bien definidas.

Categorias/relevancias base:

- Materia prima general.
- Insumo critico de apertura.
- Preparado operativo.
- Producto terminado listo para venta.
- Consumible critico.
- Consumible general.
- Producto vendible.
- Producto oculto/no operativo.

La pantalla de apertura debe excluir cosas generales y mostrar solo lo relevante
segun categoria/configuracion.
